# Проверка на примерах организаторов

Два выданных совещания — первый набор для ручной проверки извлечения поручений.
`references.json` содержит строки итоговых таблиц из DOCX, а не результат модели.
Этот набор предназначен для оценки и не должен импортироваться приложением или
использоваться как готовый ответ при обработке записи.

| Пример | Аудио: длительность по метаданным | Эталон из DOCX |
| --- | --- | --- |
| Совещание №1 | 274,296 с (4:34), mono, 48 kHz | 10 групп поручений, две таблицы |
| Совещание №2 | 206,064 с (3:26), mono, 48 kHz | 6 групп поручений, вторая таблица |

В первом совещании обсуждаются химическая промышленность и безопасность,
во втором — показатели направлений, поставщики, подрядчики и обучение.
В каждом тексте обозначено пять выступающих. Это сведения из документов,
а не проверка количества голосов в MP3. Выполнена ручная проверка двух live-Qwen прогонов и стенограмм. Результаты и ограничения приведены ниже; число меток говорящих не доказывает их правильность.

## Локальная проверка исходников

В репозитории есть два оригинальных DOCX в `evaluation/organizer/source/`. Имена MP3 в этом каталоге — относительные символические ссылки на `backend/samples/`; повторно хранить аудио не требуется. После клонирования на Linux выполните из корня:

```sh
python3 evaluation/organizer/check_samples.py --source-dir evaluation/organizer/source
```

Фактическая проверка завершилась с кодом 0: совпали размер и SHA-256 всех четырёх файлов, 10 групп поручений первого DOCX и 6 групп второго. Проверяемые имена:

- `Протокол_совещания№1.docx`
- `Протокол_совещания№2.docx`
- `Совещание №1.mp3`
- `Совещание №2.mp3`

[Сохранённый результат с хешами](source-check.json). Команда проверяет исходники и соответствие таблиц, а не точность ASR, диаризации или языковой модели. При отключённой поддержке символических ссылок поместите MP3 из `backend/samples/` в отдельный каталог с указанными именами вместе с DOCX и передайте его через `--source-dir`.

## Выполненная ручная оценка

Модель `protokol-qwen3.5:4b`, контекст 16K, явно заданная дата 2026-09-23. Эталонные таблицы не подавались модели. Приложение получало аудио, затем инструменты читали распознанную стенограмму.

| Наблюдение | Совещание №1 | Совещание №2 |
|---|---|---|
| Групп в эталонных таблицах | 10 | 6 |
| Получено поручений в проверенном live-прогоне | 11 | 8 |
| Группы с соответствующим выходным поручением | 10/10 | 6/6 |
| Существенные дефекты | Согласование бюджета назначено председателю вместо Тимура; сокращена часть содержания; два перекрывающихся юридических поручения | Сохранён ранний срок поиска поставщика вопреки позднему изменению; срок изменения договора распространён на уведомление; ошибки в цитатах |
| Имена | 8/10 имён исполнителей групп совпали точно; вариант отчества Тимура и один неверный исполнитель | Личности узнаваемы, но из имён исполнителей точно записан только Ерлан |
| Метки говорящих | 5; совпадение количества не доказывает правильность | 6 при пяти выступающих в тексте; дополнительный короткий фрагмент |

Это ручное сопоставление групп, **не 100% точности**: соответствующее поручение может содержать неправильного исполнителя, неполный смысл, неверный срок или недостаточную цитату. WER и DER не измерялись: нет проверенного пословного текста и временной разметки голосов.

В записи №2 финальные сроки расходятся с документом: поиск альтернативного поставщика — «неделя, максимум 10 дней», изменение договора — «не больше недели». Независимый локальный проход Whisper-medium по заключительному фрагменту воспроизвёл обе фразы. Это подтверждение двумя моделями, а не ручная акустическая разметка; нельзя автоматически считать следование этим словам галлюцинацией модели.

Подробности: [общий аудит](accuracy-summary.md), [поручения №1](accuracy-meeting-1.md), [поручения №2](accuracy-meeting-2.md), [стенограммы и говорящие](accuracy-transcription.md).

Отдельно проверен Docker `scripted:auto` на записи №2: 472 секунды CPU-обработки, 22 сегмента, один кандидат, подтверждение `verified`, PDF 53 872 байта, счётчик внешних соединений 0. [Результат](../docker-smoke.json). Scripted-режим выбирает максимум три кандидата и не сопоставим с live-Qwen по полноте.

## Как читать эталон

- `source_table` и `source_row` — номера с единицы; строка заголовков имеет номер 1.
  В совещании №2 первая таблица содержит показатели, а не поручения.
- `task`, `owner`, `due_text` сохранены из таблиц без перефразирования.
- `deadline_kind` — наша аннотация типа срока. Она не является полем документа
  или требованием к схеме backend.
- Дата совещания и год в документах не указаны. Поэтому `meeting_date` и
  `due_date` равны `null`, даже для «15 октября». Для отдельного теста нормализации
  можно явно задать дату и записать её в отчёт как предположение; нельзя молча
  использовать текущую дату компьютера или дату хакатона.
- `speakers_in_document` перечисляет выступающих в тексте. Это не справочник
  всех исполнителей. Таймкоды эталона отсутствуют: их надо разметить по аудио.
- Число строк — число **групп** поручений. Модель может корректно разбить одну
  составную строку на несколько задач. Точное совпадение количества задач
  или текста не является метрикой качества.

## Сложные случаи, которые нужно показать на демо

| Пример / группа | Что проверяем |
| --- | --- |
| №1 / M1-A01–A05 | Поручения озвучивает председатель, но исполнители другие. Говорящий и ответственный — разные сущности. |
| №1 / M1-A04 | «Юридический департамент» — допустимый исполнитель-организация; не придумывать имя юриста. |
| №1 / M1-A06 | Расторжение договора обусловлено систематическими нарушениями. Не выдавать условное действие за уже принятое безусловное решение. |
| №1 / M1-A07 | Срок обсуждают: две недели → три недели → 15 октября. Сохранить окончательный срок, не создавать три поручения. |
| №1 / M1-A08–A10 | Сохранить «следующая неделя», «текущая неделя», «среда» без выдуманной календарной даты. |
| №2 / M2-A01 | Исполнитель Ерлан не выступает. Не добавлять ему голос и не придумывать полное имя. В финальном пересказе упомянута Ботагоз; подробное поручение и таблица называют Ерлана. |
| №2 / M2-A04 | «После совещания с подрядчиками» — зависимость от события; даты события нет. |
| №2 / M2-A05 | Одна неделя относится к смете, месяц — к закрытию очереди обучения. Внешний тренер нужен «если нужно». При разделении группы сохранять область действия каждого срока. |
| №2 / M2-A06 | «Пять рабочих дней» — условие выставления счёта, не срок подготовки уведомления. Таблица не задаёт срок; в заключении аудио появляется «не больше недели» для изменения договора. Не распространять его автоматически на уведомление. |
| Оба | Повтор в заключительном резюме не должен создавать дубликаты поручений. |

Итоговые таблицы — удобный эталон, но сокращают контекст. Например, для №1
в саммари сказано, что инструктажи формальны, тогда как в диалоге это предположение
«скорее всего». При оценке фактов и условий возвращаемся к диалогу и аудио.

## Воспроизводимый прогон на ноутбуке с NVIDIA

1. Зафиксировать git SHA, модель и её версию/квантизацию, GPU/VRAM, язык,
   параметры обработки, явную дату совещания (либо её отсутствие).
2. Запустить сверку исходников выше. Подать приложению только MP3.
   Для отдельной оценки извлечения из текста брать только диалог **до** раздела
   «Саммари по ключевым пунктам», исключив готовые таблицы и ответы.
3. Сохранить сырой транскрипт, сегменты говорящих, JSON поручений, протокол,
   время первого и повторного прогона. Эти результаты не являются эталоном.
4. Вручную сопоставить результат с группами M1-A01…M1-A10 и M2-A01…M2-A06.
   Для каждой записать: найдена ли задача, верен ли исполнитель, сохранён ли
   смысл срока/условия, есть ли цитата и переход к нужному фрагменту аудио.
5. Отдельно перечислить пропуски, лишние и повторные задачи, выдуманные
   исполнители/даты. Для составных групп проверить все действия; частичное
   покрытие помечать отдельно, не считать полностью найденным.

Формат строки отчёта:

| Reference ID | ID задач модели | Полное / частичное / пропущено | Исполнитель | Срок и условия | Цитата / таймкод | Ошибка |
| --- | --- | --- | --- | --- | --- | --- |
| M1-A01 | … | … | … | … | … | … |

Для короткого отчёта достаточно показать полное покрытие групп `N/10` и `N/6`,
число частичных совпадений, ошибок исполнителя и срока, лишних задач и дубликатов.
Это ручная оценка по смыслу, а не автоматический exact-match по строкам JSON.
Для скорости считать RTF = время обработки / длительность аудио; отдельно
указывать загрузку моделей и прогретый запуск. Без прогона не заявлять точность
или скорость. Для WER/DER нужны отдельно проверенные транскрипт и временная
разметка голосов; сводные DOCX не заменяют эту разметку.

Эти два русскоязычных текста не покрывают казахскую речь, смешение RU/KK,
перебивания и длинные записи. Для этих сценариев нужен отдельный набор записей.
